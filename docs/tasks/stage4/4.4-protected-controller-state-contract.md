## Provisioning and exclusive ownership

Trusted launch supplies an absolute, dedicated state directory owned by the
configured non-root Controller UID, with mode `0700`. Startup checks that the
real and effective service UID match that identity. Walk with pinned directory
descriptors through root-owned, non-group/world-writable ancestors. Reject
symlinks, unsafe permissions and access/default ACLs. Hold a nonblocking
exclusive `flock` on the ultimate pinned directory for provisioning and for
the entire runtime store lifetime, including both listeners and cleanup.
This protects against overlapping processes using the same state directory.
Same-UID processes and the host administrator remain trusted.

Explicit provisioning under the Controller UID requires an existing empty
state directory. It exclusively creates the fixed `controller.sqlite3` as
a single-link regular file with mode `0600` and installs the versioned schema.
Ordinary startup opens the existing database in read/write mode without
creation. Checks precede SQLite open and cover owner, mode, file type, link
count, and ACLs of the database and any expected rollback journal. Keep the
directory descriptor pinned through open, operation and cleanup. Foreign
entries, including WAL/SHM files, prevent startup. Use SQLite rollback journal
mode DELETE, synchronous EXTRA, foreign key checks, and trusted schema OFF.
Verify the application identifier, exact schema and version, and integrity.
Missing, unreadable, unexpected, or corrupt state fails closed. A failed or
ambiguous provisioning attempt leaves any existing artifact unavailable for
automatic reprovisioning. SQLite's normal verified hot-journal rollback is
allowed; operators must resolve other recovery outside this authority path.

## Durable session, grant and decision evidence

A startup transaction invalidates all previously active authority and
records a new server-generated session and run before either listener
can bind. The session freezes the configured Controller, requester/operator
UID-to-principal and role map, agent UID and principal, and exact existing
`mock.get_health` / `demo-api` / `local-mock` scope. Each grant durably binds
its server-generated ID, issuer UID and principal, delegate UID and principal,
session and run, proposal scope, and wall and suspend-aware expiry deadlines.
No previous-session evidence is recovered into live authorization, even when
a recorded deadline is still in the future. Restart retains history and
invalidates previous grants without comparing clocks across sessions.

Stage 4.3's serial Controller remains the linearization boundary. For issue
and revoke, commit the guarded state transition and its matching event in one
SQLite transaction before changing live authority or replying. Authenticate the
operator for the requested role and ownership. A grant can be issued at most
once per session. Revocation and expiry are terminal. Observe either expiry
at equality, persist the terminal transition, and deny new admission. Check the
current session, exact live grant binding and positive PDP verdict for every
admission. Persist required decision evidence before the existing final
deadline/clock check and positive reply. The commit-to-reply check preserves
the wall and suspend-aware expiry gates even when storage is slow.

SQLite, authorization-store, integrity, capacity, failed/ambiguous commit or
required journal errors stop both listeners and abandon the session. Send no
new success after an uncertain commit and do not retry the transaction to
recover authority. If a confirmed transition's reply is lost, it remains
durable and may be inspected only within the same live authorized session.
A decision record is not proof of reply delivery or an effect. Expiry and
revocation prevent future authorization; already-sent bytes are unaffected.

Persist only server-owned identifiers, trusted configuration and bounded
decision/lifecycle evidence. Keep the Stage 4.3 frame, rate and connection
budgets. Limit stored sessions to 256 and combined retained events to 8192
per database, with bounded field sizes and no automatic evidence deletion.
Capacity is checked transactionally and exhaustion fails closed. Keep one
bounded grant per session. These limits are local design choices, not a
retention or availability claim. Durability relies on the supported native
Linux filesystem and SQLite's documented transaction guarantees. Process
interruption tests exercise recovery and uncertainty, not hardware power
failure or resistance to a privileged host administrator.

## Integration scope and evidence

Add an explicitly selected protected Controller entry that shares Stage
4.3's serial serving loop, IPC frames, authentication and policy. Preserve the
existing Stage 4.2 and 4.3 fixture entries and their marker assertions.
Keep legacy application/database launch paths independent. The Stage 4.4
change does not prepare pending actions, authorize human approvals, reserve
dispatch or execute a target mutation. Those capabilities require the
subsequent work packages and their own verified exact action bindings.

Local evidence covers directory/file ownership, mode and link/ACL rejection,
owner contention, missing/corrupt/wrong-schema startup, durable exact
binding and transition/evidence atomicity, restart invalidation, expiry
and revocation persistence, audit/capacity failures, process interruption,
and pre-commit and post-commit failure injection with no positive reply.
Existing Stage 4.1–4.3 behavioral, wire and ordinary CI evidence still apply
at their verified revisions. Record exact local commands and distinguish
real crashes from injected commit ambiguity.

Native evidence uses the approved disposable runner and the verified
executable staging setup. Use a protected private state directory under a
validated writable `/run` for the fixture. Database files require no executable
mount. The trusted root harness provides root-owned ancestors and the
Controller-owned `0700` final directory. It drops UID before provisioning,
serving, or inspecting SQLite, and keeps the tested service identities
distinct. Verify operator and agent denial of filesystem database access and
simultaneous Controller denial, durable issue/revoke transitions and evidence,
and restart under the same state directory with a fresh session and old
authority denied. Preserve the previous 17 markers exactly and require each
new marker once, successful job completion, and independent verification at
the exact merged revision. Formal owner acceptance remains separate.

Implementation file scope is the protected Controller store, Stage 4.3
Controller and admission integration, focused state tests, native setup,
native probe utilities and workflow, acceptance plan, campaign ledger and
its documentation checks.
