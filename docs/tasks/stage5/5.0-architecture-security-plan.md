## Objective

Give a local operator a bounded, evidence-backed answer to one question:
what is known about an unresolved simulated dispatch? Show separately what
the Controller recorded, what the Target can confirm, and what remains
uncertain. Start with read-only inspection and deterministic evaluation.
Operator disposition initially means documenting an observation or escalating
through the existing owner process, with no change to execution state.

The first implementation package excludes live store access, IPC changes,
CLI and web surfaces, schema changes, new dependencies, model calls and
external services. Stage 5 planning preserves the Stage 4 restrictions on
real effects, automatic mutation retries and credential or privilege expansion.

## Stage 5.1 interface and capture boundary

Proposed file allowlist is `adaptive_agentops/offline_reconciliation.py`,
`tests/test_offline_reconciliation.py`, `evaluations/stage5_offline_cases.json`
and the Stage 5 progress ledger. The input is a versioned synthetic case for one
dispatch. A bounded decoder accepts UTF-8 JSON bytes up to 64 KiB, with one
Controller and one Target observation and at most 16 evidence rows per
source. Reject unknown fields, duplicate keys, unsupported versions and
invalid types. The projector takes validated immutable values and returns
a typed classification, source facts and bounded reason codes. A pure
formatter emits bounded text or deterministic JSON. No filesystem, runtime
or network access belongs in these functions.

Each source carries a synthetic capture identifier, observation order and
coverage status. Model unavailable, partial and invalid sources explicitly.
Represent absent database, corrupt schema and interrupted capture as modeled
source faults. The first slice has zero database access, including offline
SQLite copies. Future capture requires a separate contract for a consistent
per-store capture by an already authorized custodian, paired provenance,
coverage and capture order, digest-verified sealed copies and a protected
read-only intake. Copying a live SQLite database file is outside that design.
Independent capture times cannot establish cross-store finality. Future intake
must verify the hardened Controller profile separately from earlier fixture
profiles and verify Target provenance independently of digest correlation.

Validation precedes classification. Invalid shape or provenance yields
`INVALID`. Conflicting valid records yield `INCONSISTENT` before any positive
result. A complete matching positive record yields `SIMULATED_EFFECT_RECORDED`.
A durable no-send record yields `CONTROLLER_NO_SEND_RECORDED`. Remaining
conclusions are `UNAVAILABLE`, `MISSING_EVIDENCE` or `UNRESOLVED` according
to source coverage and observed rows. Source facts remain separate. No
classification confers execution or retry authority.

Require a Controller anchor with consistent reservation, action, approval
consumption, session and run bindings. The request digest may be missing
before send. A persisted digest alone provides no proof of send. Historical
approval records are evidence only. The projector never calls the live
approval helper, which checks expiry against the wall clock. A Controller
positive requires its durable success outcome, corresponding event and effect evidence with matching digest and effect number. A Target positive
requires the anchored Controller digest and a matching claim for the exact
dispatch and action, with a valid committed effect number. Target rows carry
no session or run ID. Resolve those bindings only from Controller evidence. A Target null
effect is distinguishable from an absent row only in a complete claim
projection. The Stage 4 lookup returns `UNKNOWN` in both cases. Neither
observation proves that no effect occurred. Treat duplicate or contradictory
records as integrity findings. Preserve original source statuses and use
allowlisted provenance labels and reason codes without raw rows or payloads.

## Deferred live evidence flow and interpretation

An eventual live read uses the existing mutually authenticated operator Unix
socket. The Controller authorizes the inspection method for the frozen
operator principal before accessing evidence. It loads one exact dispatch's
stored reservation, status and digest, and checks their session, action and
target bindings. Only then may the Controller perform one bounded read-only
lookup on the authenticated Target connection using the stored dispatch ID,
action ID and digest. The operator supplies an inspection identifier. The
Controller owns the lookup scope, endpoint and correlation data.
[Controller dispatch state](../../../adaptive_agentops/stage4_boundary/dispatch_state.py)
· [Target receipt lookup](../../../adaptive_agentops/stage4_boundary/target_state.py)

| Observed evidence | Operator-facing interpretation |
| --- | --- |
| Validated Controller commit record or exact Target committed receipt | Report the recorded simulated effect and identify its source. Receipt evidence can resolve the effect question even when the Controller's original result is `UNKNOWN`. Preserve that original result. |
| Confirmed Controller `RESERVED_NO_SEND` | Report the Controller's durable pre-send stop for this attempt. A conflicting positive receipt is an inconsistency requiring investigation. |
| Reservation with missing outcome, or Controller `UNKNOWN` with Target `UNKNOWN` | Preserve uncertainty. The Target lookup intentionally does not distinguish a missing record from a retained claim without a receipt. |
| Target unavailable, deadline elapsed, or evidence extraction failed | Report source availability separately. Missing or unavailable evidence provides no basis to conclude that the effect was absent. |
| Mismatched identity, correlation, receipt number or contradictory durable evidence | Decline to resolve the dispatch and report a bounded inconsistency reason without returning raw storage or transport details. |

The two stores are observed separately. Record the source and observation
boundary for each result. Mixed-time, missing or contradictory observations
produce no retry or approval authority. Repeated reads may return newer
evidence, with no mutation send, reservation, approval consumption or rewrite
of original audit rows.

## Threat controls and operational limits

- Keep trusted Linux kernel, host administrator, launch configuration and
  service identities explicit. The operator UID identifies an OS principal
  shared by processes running under that UID. Physical presence, MFA and
  distributed identity are outside the Stage 4 evidence.
- Use default-deny per-method and per-resource disclosure. The live authorization
  proposal is an explicitly scoped inspection permission in the existing
  operator map. Review and approve which UID may hold it, which historical
  sessions it may inspect, and whether access itself requires a durable audit.
  Agent, requester and approver roles gain no implicit inspection scope.
- Preserve store ownership, leases, schema checks and application profiles.
  Favor reads inside the existing protected Controller boundary. An inspection
  must never start a new Controller session, change grant state, provision
  storage, or make databases accessible to the operator's OS account.
- Bound requests to one dispatch and one Target lookup with a finite deadline.
  Permit only typed status, correlation and bounded reason fields in the
  authorized response. Use aggregate outcome, evidence availability and
  latency counts for local evaluation. Exclude raw rows, paths, operator IDs,
  payloads, secrets and dynamic labels from telemetry.
- Preserve unresolved and replay evidence and fail closed at capacity. Stage 4
  cap behavior remains authoritative. Before any recovery design is approved,
  define paired-store provenance, access and retention rules, integrity checks
  and isolated restore drills. A restored snapshot confers no live authority.

## Proposed evidence and release gates

Freeze the synthetic case manifest and expected outcomes before implementing
the projector. Cover confirmed outcomes, target-confirmed effects following
lost acknowledgement, no-send records, missing records, unresolved claims,
source failures, stale or mixed observations, invalid inputs, mismatched
correlation, and conflicting records. Record the case version and SHA-256 of the frozen manifest before running scored evaluation. Require every case to match its
expected status, provenance and allowed fields. Independently verify zero
state changes, reservations, approval consumptions and mutation sends.
Report denominators, failed cases, source availability and measured latency
from the exact revision. Stage 3's consumed holdout remains historical
evidence.

A separately approved live inspection package must also verify wrong UID,
wrong role and wrong endpoint denial, disclosure limits, timeout, corrupt or
unavailable state, and isolation from mutation entry points. Run focused and
full ordinary CI, then require exact-diff independent security review. Any
native evidence requires a newly authorized runner and dispatch budget.
The closed Stage 4 campaign supplies historical evidence.
