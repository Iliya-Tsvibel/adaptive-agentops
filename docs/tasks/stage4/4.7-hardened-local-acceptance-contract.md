# Stage 4.7 hardened local acceptance

Base: `bb4fd26505993a7ce93f656f795024fcef86148c`.
Authority: [Stage 4 campaign](../../campaigns/stage4-autonomous-completion.md)
and [ADR-0001](../../decisions/ADR-0001-stage4-identity-boundaries.md), D01–D10.

| Decisions | Integration acceptance criteria |
| --- | --- |
| D01–D03 | Use distinct agent, Controller, target, requester and approver UIDs, mutually authenticated Unix endpoints, and a frozen server-owned session, principal map and target endpoint. No caller supplies a run or principal. |
| D04–D05 | Only the mapped requester can issue and revoke the one bounded restart grant. The agent submits a typed proposal. The Controller authenticates the agent, checks grant scope and state, runs the PDP and durably records at most one immutable pending action. Only the configured approver can inspect the action and explicitly approve or reject the exact action ID and fingerprint. Use Stage 2 action and approval persistence, including committed-action validation. |
| D06 | An explicit approver dispatch request uses the same authenticated operator boundary. Recheck the live durable grant, current session, immutable action, exact unconsumed approval, current PDP decision, endpoint and deadlines. On the authenticated target connection, atomically consume approval, reserve dispatch and append evidence. Use one in-memory permit and one send. |
| D07, D10 | Use the existing protected target replay and SQLite-only effect protocol. Persist the exact request digest before sending. Retain correlated receipts and unresolved evidence. Deny at capacity or on required state or audit failure. Ambiguous reservation or approval commits grant no execution authority. Ambiguous sends or replies grant no retry authority. |
| D08–D09 | Use a protected hardened profile and separate launch entry point. Keep legacy and isolated Stage 4.1–4.6 probes unchanged in authority and evidence. Restart invalidates old live grants and pending authority while retaining evidence. |

An approved decision establishes that the request came from a process under
the configured operator UID. The OS identity supplies neither physical-human
presence nor MFA. The owner-authenticated native workflow exercises that
boundary with disposable test processes under distinct UIDs.

## File scope and exclusions

Scope covers the Stage 4 boundary and its integration with existing Stage 2
action and approval persistence, focused tests, existing cumulative native
harness and workflow, and task, evidence and campaign documentation. Scope
excludes new credentials or bearer tokens, general-purpose operations, real
effects, dependency changes, legacy authorization changes and production.

## Evidence and gates

Run deterministic local checks for success, missing authority, policy denial,
rejection, expiry, revocation, role and peer identity, wrong action binding,
approval reuse, ambiguous commit or result, audit failure, replay and restart.
Retain all 28 previous native markers. Add native markers for UID-bound
proposal and operator decision, correlated end-to-end effect, denied
authority, and restart or interrupted effects. Require exact-diff review,
ordinary CI and an independent review of actual cumulative native evidence.
Count each fresh native dispatch against the campaign cap of eight.
