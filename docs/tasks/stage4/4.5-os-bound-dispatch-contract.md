# Stage 4.5 OS-bound dispatch authorization

Base revision: `e5ea24b7a4954d76e2de3a2c57b6eac8a6b0e943`.
Scope: D06 and its dependencies on D01–D05, D08–D10 of [ADR-0001](../../decisions/ADR-0001-stage4-identity-boundaries.md).
This package verifies a Controller-authorized dispatch to the isolated
simulated `demo-api` target with a no-effect acknowledgment. Production remains
NO-GO. [Campaign contract](../../campaigns/stage4-autonomous-completion.md)

## Scope and source of authority

Use dedicated Controller and target UIDs and the existing
`Link.CONTROL_TARGET` protected Unix socket. Verify the target and pin its
authenticated connection before opening the reservation transaction. The
target verifies the configured Controller UID before reading any request
bytes. Paths, target identity, principals and policy are established by
trusted launch configuration and frozen for the Controller session. There
is no JWT, signing step, bearer credential, TCP path or legacy fallback.

Only the trusted, isolated acceptance harness may provision the no-effect
restart fixture. It creates a fresh current-session and run bound to one
exact restart scope, a synthetic approved pending action, and fixture
operator evidence in the protected store. It uses a frozen, mapped
approver UID and principal distinct from the agent. These rows are
synthetic verification inputs. They do not establish that a live human
approval was authenticated. There is no public restart request, agent or
operator IPC route to create this fixture, or public endpoint to initiate
dispatch. The private Controller coordinator consumes the protected
fixture as a no-effect test of the authorization boundary.

The exact scope is `mock.restart_service` for `demo-api` in `local-mock`,
with an empty argument object. Stage 4.3 health grants and proposal
verdicts cannot authorize restart. Stage 2/3 records, the legacy CLI,
stored reservations alone, other sessions, and caller-supplied identity
or authority are ineligible. The target only authenticates, validates and
acknowledges the tested envelope. It never changes a counter, restarts a
service or performs any other target effect in this package.

## Protected state and reservation

Use the Stage 4.4 Controller directory lease and protected SQLite
invariants. Add an explicit dispatch-fixture schema profile for fresh
disposable state under the existing one-time, empty-directory provisioning
rules. Normal startup requires the exact expected profile and schema and
opens without creation. Existing Stage 4.4 data is left intact. No implicit
upgrade, state reset, history deletion, or import of legacy authority.
Persist immutable fixture scope and grant bindings, pending action, approval,
reservation, and correlated evidence. Keep the proposal-only profile and
earlier fixture entry points available on their existing terms.

Reuse the existing `MockRestartServiceProposal`, `PendingRestartAction`,
`RestartApproval`, version-1 action fingerprint serialization and PDP.
Keep the canonical fingerprint bytes and strict field/type validation.
The dispatch reservation must also bind fields deliberately excluded
from that fingerprint, including session, exact action, grant and approval
IDs, expiry and target. Use a single protected database transaction for
reservation and evidence rather than routing into a legacy coordinator that
owns an independent transaction or accepts a caller-selected path.

The serial Controller opens `BEGIN IMMEDIATE`, verifies its persisted active
session and frozen current bindings, loads the exact pending action and
unconsumed approved decision, and checks fresh PDP
`APPROVAL_REQUIRED`, exact scope, fixture issuer/delegate roles and binding,
and strict current wall and suspend-aware elapsed deadlines. Conditionally
consume the exact approval once, insert one reservation unique by action and
approval with a server-generated dispatch ID, and append binding and
pre-dispatch evidence in the same transaction. A capacity, validation or
known rollback failure sends zero requests. An ambiguous COMMIT or uncertain
cleanup invalidates the live Controller session and grants no send permit.

After a confirmed commit, only the live coordinator receives a process-local,
single-use permit bound to the authenticated target connection and that
reservation. Construct the exact envelope, check clocks and expiry again,
consume the permit before entering the one bounded application send call,
and close the connection at completion or failure. Envelope construction
failure or expiry burns the opportunity. No path reconstructs a permit from
persistent evidence or reconnects and resends. Preserve consumed approvals,
reservations and unresolved evidence through restart and capacity failures.

## Envelope and acknowledgment

Use a dedicated, bounded, versioned dispatch frame with an exact
length-prefixed UTF-8 JSON body. Reject duplicate or unknown fields, invalid
encoding, trailing bytes, unsupported versions, malformed and overlong
input, and more than one request or response on a connection. Keep existing
proposal, operator and handshake protocols unchanged. Bind the message to:

- Version, fixed simulated-restart message type and configured target.
- Controller session, run, grant, dispatch, action and approval IDs.
- Frozen requester and agent principals and policy correlation.
- Exact canonical scope, arguments, fingerprint version and fingerprint.
- Issue time and a short, no-grace dispatch window bounded by the earliest
  action, approval, and fixture grant expiry, with a five-second maximum.

The target independently checks the peer UID, type/version, configured
target, exact fixed scope, canonical fingerprint and both time bounds before
acknowledging. It trusts the authenticated Controller's committed approval
assertion, without reading its mutable state. The reply on the same verified
connection must correlate the exact dispatch and action and explicitly
report no effect. A valid reply supplies acknowledgment evidence only.
Stage 4.6 will add durable target claims, replay exclusion, effect and
receipt handling. Stage 4.7 will supply an end-to-end live authenticated
operator approval chain.

Preserve the existing one-second connection bound and two-second cooperative
frame/exchange rules. Fail closed for clock regression, excessive divergence,
missing time, expiry at equality or future-issued authorization. No skew
grace is authorized. A known failure during envelope construction records no send.
Once the exchange function owns the attempt, a fault is recorded
conservatively as unknown, including an exception in the final pre-send
check. A missing, invalid or lost acknowledgment is also unknown. Record
the bounded correlated outcome when possible. A failed or ambiguous
outcome write leaves durability unconfirmed and never revives authority. Restart invalidates in-memory permits and prior
session authority even if an existing reservation is still present.

## Verification and progression

Verify strict frame, canonical fingerprint, exact cross-action and
cross-session binding, policy and approval denial, consumed approval, missing
or expired/revoked fixture grant, clock and deadline boundaries, and rejection
of a wrong target before reservation. Test concurrent or repeated reservation
for one winner, exact commit of approval/reservation/audit, pre-commit
rollback, ambiguous commit before and after durable write, crash or expiry
after reservation, lost/malformed acknowledgments, and no rehydration or
resend. Count actual application sends and verify zero on every
pre-authorization failure. Keep fixtures for denied input and no-effect
acknowledgment distinct from durable target effect or replay claims.

On the approved native runner, keep prior marker inventories intact and add
distinct-UID evidence of Controller/target mutual authentication, wrong-peer
rejection before bytes or reservation, exact current-session fixture
binding, one post-commit application send, and a matching no-effect
acknowledgment. Record the bounded logs, exact native/CI revisions and
independent verification. Formal owner acceptance remains separate.

Implementation file scope is the protected-store dispatch profile,
simulated reservation and wire modules, focused dispatch tests, native
fixture and workflow, acceptance plan, campaign ledger and its documentation
checks.
