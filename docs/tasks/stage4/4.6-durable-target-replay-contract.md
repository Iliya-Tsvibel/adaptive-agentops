# Stage 4.6 durable target replay and effects

Base revision: `6d618afd6bd33328ef9ecda0a99e023a86afaa8b`.
Scope: D07 and D10 of [ADR-0001](../../decisions/ADR-0001-stage4-identity-boundaries.md).
The [campaign contract](../../campaigns/stage4-autonomous-completion.md) limits
effects to SQLite simulation for `demo-api` in `local-mock`. The
[Stage 4.5 contract](4.5-os-bound-dispatch-contract.md) supplies the existing
authenticated Controller reservation and single-send rules. Stage 4.7 owns
end-to-end authenticated human approval.

## Protected target state

Provision one explicitly empty target-UID-owned directory using the existing
Linux protected-directory and private-file checks. Require a separate target
database and its exact schema, durability settings and integrity at normal
startup. Lease the state directory for the lifetime of the serving process.
Missing, invalid, or unavailable state prevents listening. Set an admission
limit of 10,000 retained claim rows and a SQLite page budget of 64 MiB, with
a bounded rollback journal. Capacity limits apply before granting new effect
authority. Preserve claimed and terminal records for the life of the instance.

## Write and receipt rules

Verify the Controller UID before reading and enforce the existing canonical
scope, action fingerprint and dual-clock window. Use a separate wire version
for the effect profile. Bind a durable claim to the dispatch and action IDs
with independent uniqueness constraints, and retain the SHA-256 digest of the
entire canonical request, including its version. Any duplicate or collision
has zero effect. A matching duplicate can be inspected via a separate
authenticated read-only receipt frame.

In a first transaction, commit the claim. Only its live caller can continue,
and only after a confirmed commit. In a second transaction, recheck expiry
and the cooperative deadline immediately before writing, then atomically
increment the SQLite simulated counter and record the correlated receipt.
A failed or ambiguous claim commit cannot authorize effects. An interrupted
claim never resumes, including after a process restart. A failed or ambiguous
effect commit yields no success reply. A confirmed effect commit permits a
correlated receipt to be sent on the same connection. Missing or indeterminate
receipt evidence leaves the Controller outcome unknown. Receipt lookup uses
dispatch ID, action ID and request digest, returns only existing state, and
grants no authority. Unknown outcomes never authorize another mutation send.

## Scope and evidence

Changes are limited to the protected SQLite helpers, dispatch coordinator and
wire, new target state, focused tests, native staging and probes, workflow
selection, evidence documents, progress ledger and documentation checks.
The Stage 4.5 no-effect profile, earlier contracts, and earlier native
marker inventories remain supported. The fixture uses the existing
synthetic approval provisioner. No networked or real infrastructure effect,
new dependency, external model call, or legacy authority import is in scope.

Use deterministic tests for uniqueness, exact correlation, capacity,
storage or schema failure, clock expiry, commit ambiguity, and interruption
between the transactions. Verify one SQLite effect and receipt, including
after abrupt process loss and restart. The cumulative native workflow must
add evidence of one correlated target effect, duplicate denial after restart,
and a retained claim after a verified process interruption. Require independent
verification of the exact diff, normal CI, and the recorded native run.
