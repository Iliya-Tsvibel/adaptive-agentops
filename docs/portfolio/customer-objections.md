# Adaptive AgentOps customer objections

The evidence applies to the bounded local profiles and revisions linked
below. Production remains **NO-GO**. TESTED means the named evidence exists;
ACCEPTED means the owner accepted that specific historical scope. For Stage
6.E, this is the [accepted native Linux, local, nonproduction scope](../campaigns/stage6e-progress.md).

| Question | Decision, answer and current limit | Status and evidence |
| --- | --- | --- |
| Can an agent bypass the Controller? | Dedicated UIDs, protected sockets and mutual kernel authentication reserve the Target path for Controller. This applies to the supported local links under trusted host enforcement. | ACCEPTED · [Stage 4 D01–D03](../stage4-acceptance.md) |
| Can the agent approve its own action? | The frozen operator map requires a distinct approver principal and exact action binding. A compromised approver UID remains within the host trust assumption. | ACCEPTED · [Stage 4 D05–D06](../stage4-acceptance.md) |
| How is the inspector authenticated? | A distinct configured UID and mutually verified kernel credentials guard the dedicated maintenance socket. The UID represents an OS principal. | ACCEPTED for Stage 6.E local scope · [Inspection tests](../../tests/test_stage6e_inspection.py) |
| Why can the inspector read but not execute? | The maintenance launch exposes only one exact dispatch query. Its request path has no grant, approval, reservation or mutation methods. | ACCEPTED for Stage 6.E local scope · [Inspection contract](../tasks/stage6e/inspection-contract.md) |
| Who can open the databases? | Controller owns its history and inspection audit. Target owns its replay store. The trusted host administrator controls provisioning. | ACCEPTED for Stage 4 stores · [Stage 4 D07–D08](../stage4-acceptance.md) |
| What does UNKNOWN do? | The original outcome is retained. A new receipt observation may refine the diagnosis while execution authority remains spent. | ACCEPTED for Stage 6.E local scope · [Inspection tests](../../tests/test_stage6e_inspection.py) |
| How is missing evidence distinguished from no effect? | Lookup UNKNOWN covers absent and claim-only evidence. Only a separately bound durable Controller no-send record establishes that outcome. | ACCEPTED for Stage 6.E local scope · [Inspection contract](../tasks/stage6e/inspection-contract.md) |
| What if Target commits and loses the acknowledgement? | A read-only lookup can recover a matching retained simulated SQLite receipt. Historical UNKNOWN remains visible. | ACCEPTED for Stage 6.E local scope · [Native acceptance](../stage6e-acceptance.md#native-linux-acceptance) |
| Can reconciliation execute again? | Projection handles typed observations; the maintenance endpoint sends only the existing Target receipt lookup and writes disclosure audit. | ACCEPTED for Stage 6.E local scope · [Inspection tests](../../tests/test_stage6e_inspection.py) |
| What if a store or the audit fails? | Missing evidence preserves uncertainty; corrupt or conflicting evidence suppresses positive attribution. Unconfirmed audit suppresses protected disclosure. Automatic recovery is deferred. | TESTED with modeled faults · [Inspection tests](../../tests/test_stage6e_inspection.py) |
| Can one customer read another customer's data? | No multi-tenant boundary is defined. One trusted local launch configures one inspector and one dispatch scope. Enterprise isolation requires a new tenancy model. | DEFERRED · [ADR-0002](../decisions/ADR-0002-stage6-evidence-bridge.md) |
| What if an authorized UID is compromised? | Processes sharing a UID share its OS authority. The inspector still has only its configured method and dispatch; compromised Controller, Target or administrator is outside this model. | ACCEPTED trust model · [ADR-0001](../decisions/ADR-0001-stage4-identity-boundaries.md) |
| Is the audit tamper-proof? | A separate protected SQLite commit gates disclosure. Trusted service and administrator access limit the integrity claim. | ACCEPTED for local audit-before-disclosure · [Inspection contract](../tasks/stage6e/inspection-contract.md) |
| How is evidence provenance established? | Controller reads one validated historic binding and performs a mutually authenticated exact-key Target lookup. Source observations are independent and carry no common snapshot claim. | ACCEPTED for Stage 6.E local scope · [Inspection tests](../../tests/test_stage6e_inspection.py) |
| How would this work in Docker or Kubernetes? | Container UID mapping, socket reachability, mounts, root capabilities and state isolation need dedicated validation. Stage 6.D tested a hybrid profile with a Docker Agent and native trusted services on disposable Linux. Kubernetes, rootless Docker and remapped identities remain outside the evaluated scope. | TESTED · [Stage 6.D assessment](../stage6d-technical-assessment.md) |
| What did Agent replacement prove? | A replacement Agent used a fresh grant. Old dispatch authority remained spent and the native Target receipt still recorded one simulated effect. | TESTED for the hybrid profile · [Stage 6.D assessment](../stage6d-technical-assessment.md) |
| What if a container or Pod loses state? | Historical retention and replay guarantees rely on protected durable storage. Ephemeral replacement and restore semantics require a separate plan and evidence. | DEFERRED · [ADR-0002](../decisions/ADR-0002-stage6-evidence-bridge.md) |
| What is the operational cost? | Maintenance holds the execution lease, requires a separate UID and audit directory, and performs bounded queries and up to one Target lookup. Production throughput and cost have no accepted measurements. | TESTED local mechanics · [Inspection contract](../tasks/stage6e/inspection-contract.md) |
| Why trust code written with AI agents? | Trust derives from scoped authority, exact-diff independent review, tests, traceable revisions and owner acceptance. Separate agent evidence does not provide human security certification. | TESTED process · [Developer loop](../developer-loop.md) |
| Which results are native? | Stage 4 has distinct-UID native evidence. Stage 5 is synthetic offline. Stage 6.E has 7 native markers on its exact acceptance runtime revision and separate ordinary tests. | ACCEPTED historical scopes · [Stage 4](../stage4-acceptance.md) · [Stage 5](../stage5-acceptance.md) · [Stage 6.E ledger](../campaigns/stage6e-progress.md) |
| What blocks production? | Remote identity, multi-tenancy, production deployment isolation, recovery, tamper-resistant auditing and real external effect semantics remain outside the accepted local scope. | DEFERRED · [ADR-0002](../decisions/ADR-0002-stage6-evidence-bridge.md) |
