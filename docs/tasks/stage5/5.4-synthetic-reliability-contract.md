**Conditional campaign authorization.** Exercise the existing offline
projector and diagnostics with controlled, in-process failure injection and

## Scope

The allowlist is this contract, `tests/test_stage54_synthetic_reliability.py`
and `docs/campaigns/stage5-progress.md`. Use existing Python and pytest.
Build fresh synthetic cases in the test module from literal data or
already reviewed fixtures. Preserve the bytes and labels of both existing
evaluation populations. Reliability checks have their own denominator and
do not contribute to Stage 5.3 accuracy. Escalate any defect requiring a
product change through a separately scoped review.

The tests call the existing offline decoder, projector and diagnostic
formatter. Fault injection uses test-scoped patching that is undone before
pytest reporting. Excluded capabilities include live or copied database
access, live snapshots, IPC, new identities or privileges, persistence,
mutation, automatic retries, recovery actions, dependencies, and native
dispatch. Stage 5 native usage remains 0/4.

## Required checks

| ID | Initial state and fault | Required safe behavior and preserved evidence |
| --- | --- | --- |
| R1 | Valid synthetic fixture, inject one `RecursionError` from the JSON parser. | One parser invocation. The public analyzer returns `INVALID` with `INVALID_FIXTURE`. Diagnostic sources remain empty. The fixture bytes and the clean control result remain unchanged. |
| R2 | Valid fixture, inject one `KeyboardInterrupt` at the parse boundary. | The call propagates interruption without returning a result or attempting another parse. Preserve the original fixture. An explicitly separate invocation after removing the injection yields the clean result. |
| R3 | Valid prior result, inject one `KeyboardInterrupt` at diagnostic serialization. | The formatter propagates interruption without returning a diagnostic or attempting another serialization. Preserve the original result. A separate invocation after removing injection yields the same diagnostic as the control. |
| R4 | Independently analyze modeled unavailable, partial-empty and complete-empty Target observations while the Controller retains an unresolved reservation. | Preserve `UNRESOLVED` without positive attribution across the sequence. Preserve source coverage, distinguish `NOT_OBSERVED` from `NO_ROW`, and retain immutable earlier results. |
| R5 | Controller has durable positive evidence. Supply an invalid Target observation, then in a separate case a later or equal-order contradictory Target observation. | Return `INVALID` or `INCONSISTENT`, respectively. No positive effect number or sources escape through either result or diagnostics. Preserve original source evidence and the clean control result. |
| R6 | Submit a valid fixture of exactly 64 KiB using trailing JSON whitespace, then add one byte. Submit validly shaped projected rows at 16 and 17 rows for one source. | Exact-size valid input retains its clean result. One byte above the limit yields `INVALID`. Valid duplicate rows within the cap yield `INCONSISTENT`, while the input above the cap yields `INVALID`. Neither over-cap case produces positive attribution. |

R1–R3 inject Python faults at named seams. They exercise interruption
and parser handling in-process. R4–R6 model evidence availability,
consistency and capacity. Unavailable and invalid observations represent
missing storage or corrupt evidence only as synthetic states. These
checks do not establish live crash recovery, operating-system interruption
behavior, storage atomicity or native acceptance.

Use call counters and fail-on-call tripwires around the units under test
for filesystem access, sockets, SQLite and logging. Restore patches
before test reporting. Run each scenario with a fresh independent input
and compare exact normalized results and diagnostics, or the same
injected exception type and call count. Check inputs before and after.
Tripwires, redaction, unexpected positive attribution and nondeterminism
are hard failures. Use fixed scenario IDs and check names in reliability
failure summaries and keep raw fixture and exception contents out.

## Evidence and merge gates

Require all six scenarios, focused and full ordinary-user pytest,
independent review of the exact implementation diff, and ordinary CI.
For each scenario record the initial state, injection or modeled
condition, expected and observed behavior, evidence preserved, recovery
limit and whether an operator would need to investigate unresolved or
conflicting evidence. An explicit separate analysis of a fresh synthetic
input is allowed. It supplies no execution, retry or repair authority.

Publish a dedicated Stage 5.4 PR and match the reviewed, CI-tested and
merged trees. Record exact revision, review, test counts, 6/6 scenario
results and residual limits in the ledger and PR checkpoint.
Production remains NO-GO.
